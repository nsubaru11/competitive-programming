## 問題に応じた実行環境の選び方

次の表は、各環境の特徴から考えた「最初に試す環境」の目安であり、このリポジトリでの速度比較結果ではない。
提出先で利用できる言語・バージョン・ライブラリを確認し、制限が厳しい場合は最大ケースに近い入力で実行時間とメモリを比較する。

| 問題・処理の特徴                                                             | 最初に試す環境       | 選ぶ理由・判断のポイント                                                                                                                              |
|------------------------------------------------------------------------------|----------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------|
| 四則演算、条件分岐、小さな全探索など、短時間で終わる処理                     | CPython              | JITの準備による利点が出にくい。短い処理ではまずCPythonで十分か確認する。                                                                              |
| 長いループ、DP、配列更新など、Pythonで同じ処理を繰り返す                     | PyPy                 | 繰り返し実行されるPythonコードをJITが最適化できる。                                                                                                   |
| BFS・グラフ探索・データ構造の操作が多い                                      | PyPy                 | Python側の反復処理が主なら候補になる。組み込み関数・ライブラリの処理が主ならCPythonとも比較する。                                                     |
| 型がそろった数値ループ、重いシミュレーション、数値中心のDP・Moのアルゴリズム | Codon                | 対応する構文・APIで書け、途中の計算も64bitに収まる場合、ネイティブコンパイルを活用できる。                                                            |
| `split/join/replace` など、文字列の組み込み処理が中心                        | CPython              | まず組み込み処理の性能を利用する。文字を1つずつ処理する長い自作ループならPyPy/Codonも比較する。                                                       |
| 巨大な整数、64bitを超えるビット集合、桁数の大きな数論処理                    | CPython              | 任意精度整数をそのまま使える。長いPythonループも多い場合は、同じく任意精度整数を持つPyPyとも比較する。Codonの通常の `int` は64bit。                   |
| NumPy・SciPyなど、既存のCPython向けパッケージを利用する                      | CPython              | この構成でパッケージをそろえている環境を利用する。PyPy/Codonへ切り替えても、同じパッケージがそのまま使えるとは限らない。                              |
| Python 3.12以降の構文・APIを利用する                                         | CPython 3.13         | このPyPyはPython 3.11相当なので、3.12以降の機能は前提にできない。CodonもCPython 3.13との完全互換ではない。                                            |
| 深い再帰のDFS・木DP                                                          | CPython / PyPyで確認 | 再帰上限に加えて、実際の深さ・メモリ使用量を確認する。必要なら明示的なスタックによる反復へ変える。Codonなら深い再帰が自動的に安全になるわけではない。 |
| 対話問題                                                                     | CPythonを起点に選ぶ  | 出力を送るタイミングが重要。`print(..., flush=True)` を使い、全入力の事前読み込みを避ける。環境の変更だけではflushの問題は解決しない。                |
| 入出力やライブラリ呼び出しが時間の大半を占める                               | CPythonを起点に比較  | JITやネイティブ化だけでは改善しにくい。まず入力の読み方・出力回数を見直す。                                                                           |
| メモリ制限が厳しい                                                           | 実測して選ぶ         | JITを含む実行環境とデータ表現の両方が影響する。配列・辞書の持ち方や入力の一括保持も含めて比較する。                                                   |

PyPyは主にPythonで書かれた処理を高速化する。JITの準備時間があり、短い処理や、既にCなどで実装された関数の呼び出しが中心の処理では利点が出にくい。
[PyPy FAQ](https://doc.pypy.org/faq.html#how-fast-is-pypy)、[性能調整の考え方](https://pypy.org/performance.html)を参照する。
Codonも、既存のネイティブライブラリ呼び出しや入出力が支配的な処理では、大きな改善が得られるとは限らない。
[Codon FAQ](https://docs.exaloop.io/start/faq/)を参照する。

## CPython 3.13.7 の特殊な設定

| テンプレートのコード                       | 意味・使う場面                                                                                                                                               |
|--------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `input = sys.stdin.readline`               | 組み込み `input()` を行入力へ差し替える。行末の改行を除去しないため、数値は `int(input())`、文字列は `input().rstrip("\r\n")` と読む。                       |
| `sys.setrecursionlimit(1_000_000)`         | Pythonが許可する再帰の深さを引き上げる。再帰DFSなどで既定の上限を超える場合に使う。高速化やスタック容量の拡張ではなく、100万段の再帰が動く保証でもない。     |
| `sys.set_int_max_str_digits(0)`            | 整数と十進文字列の相互変換にある桁数制限を解除する。例えば5000桁の入力を `int(...)` にする場合に関係する。整数演算自体の精度や再帰上限を変える設定ではない。 |
| `T = TypeVar("T", int, float, str)`、`Any` | IDEの型検査・補完のための型ヒントに使う。値を機械語の整数へ固定したり、実行を高速化したりする設定ではない。                                                  |

行入力の差し替えは、空行では `"\n"`、EOFでは空文字列を返す。改行だけを取り除く場合は `rstrip("\r\n")` とし、末尾の空白まで取り除く
`rstrip()` と使い分ける。
再帰上限・整数の文字列変換上限の仕様は [Pythonのsysリファレンス](https://docs.python.org/3.13/library/sys.html)を参照する。

## PyPy 3.11 / 7.3.20 の特殊な設定

行入力、再帰上限、整数の文字列変換上限、型ヒントはCPython版と同じ目的で設定している。
追加しているのは次のJIT設定である。

```python
try:
  import pypyjit

  pypyjit.set_param("max_unroll_recursion=-1")
except ImportError:
  pass
```

| コード                     | 意味・使う場面                                                                                                                        |
|----------------------------|---------------------------------------------------------------------------------------------------------------------------------------|
| `import pypyjit`           | PyPyのJITを調整する専用モジュールを読み込む。                                                                                         |
| `max_unroll_recursion=-1`  | 再帰関数をJITで展開する設定を調整し、再帰の展開を抑える。再帰を多用する処理で比較する設定であり、すべての問題が速くなるわけではない。 |
| `except ImportError: pass` | CPythonで確認・デバッグするときに、PyPy専用モジュールがなくても起動できるようにする。CPythonでこのJIT設定が有効になるわけではない。   |

`max_unroll_recursion` は再帰の許可深さを変える設定ではない。深さの上限は `sys.setrecursionlimit` と別である。
速度が問題になる場合は、この設定の有無を同じ入力で比較する。
型ヒントを加えること自体はJITの高速化スイッチではない。
[JITパラメーター](https://doc.pypy.org/jit_help.html)、[型ヒントと性能](https://doc.pypy.org/faq.html#would-type-annotations-help-pypy-s-performance)
を参照する。

## Codon 0.19.3 の特殊なコード・実行方法

```bash
codon run --release solution.py
```

| コード・仕組み                     | 意味・使う場面                                                                                                                    |
|------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------|
| `--release`                        | 最適化付きでネイティブコードへコンパイルして実行する。`sys` の設定で高速化するのではなく、コンパイル時の最適化を利用する。        |
| 引数の型を省略した関数             | Codonが呼び出し元から型を推論し、その型に合わせたコードを生成する。このテンプレートでは未対応の `typing.TypeVar` を読み込まない。 |
| 組み込み `input()`                 | Codonのネイティブ実装で行入力を行い、改行を除去する。CPython/PyPy版のような `sys.stdin.readline` への差し替えはしていない。       |
| 通常の `int`                       | 符号付き64bit整数であり、CPython/PyPyの任意精度整数とは異なる。値だけでなく、掛け算などの途中値も範囲に収まるか確認する。         |
| CPython向けの `sys` 設定を入れない | 0.19.3では `sys.setrecursionlimit`・`sys.set_int_max_str_digits` などを同じようには使えない。CPythonの実行設定をコピーしない。    |

[Codonの型推論](https://docs.exaloop.io/language/generics/)、[整数型](https://docs.exaloop.io/language/lowlevel/)を参照する。
Pythonとの互換性は完全ではなく、0.19.3で使える構文・標準APIを確認する。このテンプレートの設定と起動は、インストール済み0.19.3でも確認している。

`codon run` はローカルではコンパイルも行う。実行時間を比較する場合は `codon build --release -o main solution.py`
で作った実行ファイルを計測し、コンパイル時間と実行時間を区別する。
CPython/PyPyは実際の提出と同様に、新しいプロセスの起動から計測し、PyPyのJIT準備時間も含める。
